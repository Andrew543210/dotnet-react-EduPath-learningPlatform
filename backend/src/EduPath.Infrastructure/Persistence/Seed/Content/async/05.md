## Класичний дедлок

```csharp
private void LoadButton_Click(object sender, RoutedEventArgs e)
{
    var data = LoadAsync().Result;   // у WPF зависне назавжди
    Grid.ItemsSource = data;
}

private async Task<List<Item>> LoadAsync()
{
    var json = await http.GetStringAsync("/items");
    return Parse(json);
}
```

Що відбувається крок за кроком:

1. UI-потік викликає `LoadAsync()`. Метод доходить до `await` і повертає незавершену задачу.
2. UI-потік викликає `.Result` і **блокується**, чекаючи завершення задачі.
3. HTTP-відповідь приходить. Продовження `LoadAsync` хоче виконатися в захопленому контексті — тобто в UI-потоці.
4. UI-потік заблокований на `.Result`. Продовження чекає на потік, потік чекає на продовження.

`.Result` блокує потік, на який чекає продовження, і обидва чекають одне одного вічно.
Те саме відбувається з `.Wait()` і `GetAwaiter().GetResult()`.

**Рішення** — `await` до самого верху стеку викликів:

```csharp
private async void LoadButton_Click(object sender, RoutedEventArgs e)
{
    Grid.ItemsSource = await LoadAsync();
}
```

В ASP.NET Core контексту синхронізації немає, тож саме цього дедлоку не буде. Але блокування однаково
займає потік пулу й під навантаженням веде до голодування — правило «не блокуй асинхронний код» діє скрізь.

## async void

`async void` — метод, який неможливо дочекатися. Викликач не отримує задачі, тож:

- не знає, коли метод завершився;
- не може перехопити виняток — він піднімається прямо в контекст синхронізації і зазвичай **валить процес**;
- тести не можуть дочекатися результату.

Використовуйте `async void` лише в обробниках подій, де сигнатуру диктує фреймворк, як у прикладі з кнопкою вище.
Усередині обгортайте код у `try/catch`:

```csharp
private async void SaveButton_Click(object sender, RoutedEventArgs e)
{
    try
    {
        await SaveAsync();
    }
    catch (Exception ex)
    {
        ShowError(ex.Message);
    }
}
```

Підступний випадок — лямбда, передана туди, де очікують `Action`: `list.ForEach(async x => await SendAsync(x))`
компілюється в `async void`, і цикл не чекає жодного відправлення. Замініть на звичайний `foreach` з `await`.

## ConfigureAwait(false)

`ConfigureAwait(false)` каже: «продовження не обов'язково виконувати в захопленому контексті».

```csharp
var json = await http.GetStringAsync(url).ConfigureAwait(false);
```

- **У бібліотеках** (NuGet-пакети, спільні проєкти) пишіть `ConfigureAwait(false)` на кожному `await`.
  Ви не знаєте, з якого середовища вас викличуть, і не повинні захоплювати UI-контекст викликача.
- **У коді застосунку ASP.NET Core** це нічого не змінює — контексту немає. Можна не писати.
- **У UI-коді** після `ConfigureAwait(false)` не можна торкатися елементів інтерфейсу: ви вже не в UI-потоці.

`ConfigureAwait(false)` не лікує дедлок у коді, що викликає `.Result`, — лише ховає його в окремих місцях.
Справжнє рішення — прибрати блокування.

## Практика

Знайдіть у своєму рішенні `.Result`, `.Wait()` і `async void` (пошук по солюшену займе хвилину).
Для кожного випадку вирішіть: замінити на `await`, залишити як обробник події з `try/catch`
або винести блокування в `Main`, де воно безпечне.
