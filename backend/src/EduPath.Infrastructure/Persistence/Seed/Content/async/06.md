## Producer/consumer без блокувань

Реєстрація користувача має надіслати вітальний лист. Відправлення через SMTP триває секунду-дві,
і змушувати користувача чекати на нього немає сенсу. Класичне рішення — черга: ендпоінт кладе завдання,
фоновий обробник забирає й виконує.

`System.Threading.Channels` — вбудована асинхронна черга, яка не блокує потоки ні виробника, ні споживача.

```csharp
var channel = Channel.CreateBounded<Email>(new BoundedChannelOptions(100)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true,
});

// Виробник
await channel.Writer.WriteAsync(email, ct);

// Споживач
await foreach (var item in channel.Reader.ReadAllAsync(ct))
    await sender.SendAsync(item, ct);
```

## Обмежений чи необмежений

`Channel.CreateUnbounded<T>()` приймає скільки завгодно елементів. Якщо споживач повільніший за виробника,
черга росте, доки не закінчиться пам'ять.

Обмежений (bounded) канал створює **зворотний тиск** (backpressure): коли черга заповнена, `WriteAsync`
асинхронно чекає, поки звільниться місце. Виробник природно сповільнюється до швидкості споживача.
Інші режими `FullMode` дозволяють відкидати найстаріші або найновіші елементи — корисно для метрик,
де важливі лише свіжі дані.

## Канал у BackgroundService

У застосунку ASP.NET Core канал реєструють як singleton, а споживача оформлюють як `BackgroundService`:

```csharp
builder.Services.AddSingleton(Channel.CreateBounded<Email>(100));
builder.Services.AddHostedService<EmailWorker>();

public sealed class EmailWorker(Channel<Email> channel, IServiceScopeFactory scopes,
    ILogger<EmailWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var email in channel.Reader.ReadAllAsync(stoppingToken))
        {
            try
            {
                using var scope = scopes.CreateScope();
                var sender = scope.ServiceProvider.GetRequiredService<IEmailSender>();
                await sender.SendAsync(email, stoppingToken);
            }
            catch (Exception ex) when (ex is not OperationCanceledException)
            {
                logger.LogError(ex, "Не вдалося надіслати лист {To}", email.To);
            }
        }
    }
}
```

Три важливі деталі:

1. **Scope на кожне завдання.** `BackgroundService` — singleton, а `DbContext` і більшість сервісів — scoped.
   Створюйте scope всередині циклу.
2. **try/catch навколо одного елемента.** Необроблений виняток зупинить увесь обробник, і черга перестане розбиратися.
3. **stoppingToken.** Хост скасовує його під час зупинки застосунку — `ReadAllAsync` завершиться, і сервіс вийде коректно.

## Обмеження каналу в пам'яті

Канал живе в пам'яті процесу. Після перезапуску застосунку незакінчені завдання зникнуть. Для листів
про скидання пароля це прийнятно, для платежів — ні. Там потрібна зовнішня черга (RabbitMQ, Azure Service Bus)
або таблиця вихідних повідомлень (outbox) у тій самій базі даних.

## Підсумок курсу

Ви розібралися, як `await` звільняє потоки і що компілятор робить із методом, як запускати незалежну роботу
паралельно й обмежувати її, як прокидати скасування від контролера до бази, як не потрапити в дедлок
і як винести повільну роботу у фонову чергу.

## Практика

Винесіть відправлення листів у своєму проєкті в канал із `BackgroundService`. Перевірте, що ендпоінт реєстрації
відповідає миттєво, а при зупинці застосунку обробник завершується без винятків у логах.
Фінальний тест перевіряє матеріал усього курсу.
