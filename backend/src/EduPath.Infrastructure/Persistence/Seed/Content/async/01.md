## Проблема, яку розв'язує async

Вебсервер на ASP.NET Core обробляє запити потоками з **пулу потоків** (thread pool). Пул невеликий:
на старті в ньому приблизно стільки потоків, скільки ядер у процесора, і нові додаються повільно —
приблизно один-два на секунду. Це зроблено навмисно: тисяча потоків з'їдає пам'ять і час на перемикання контексту.

Уявіть ендпоінт, що читає профіль користувача з бази даних. Запит до бази триває 200 мс. Якщо код синхронний,
потік усі ці 200 мс просто чекає відповіді мережі й нічого не робить, але однаково вважається зайнятим.
Під навантаженням усі потоки пулу опиняються в такому очікуванні, нові запити стоять у черзі,
а процесор при цьому завантажений на 5 %. Це явище називають **голодуванням пулу потоків** (thread pool starvation).

## Що змінює await

Асинхронний код повертає потік у пул на час очікування введення-виведення:

```csharp
// Блокує потік на весь час запиту до бази
var user = db.Users.First(u => u.Id == id);

// Потік повертається в пул, поки база відповідає
var user = await db.Users.FirstAsync(u => u.Id == id);
```

Поки драйвер бази чекає відповіді від мережевої карти, жоден потік не заблокований. Коли дані приходять,
операційна система сигналізує про завершення операції, і продовження методу виконується на будь-якому вільному потоці.
Той самий сервер з тими самими ресурсами витримує в рази більше одночасних запитів.

## Чого async не робить

- **Не прискорює окремий запит.** Запит до бази триває ті самі 200 мс. Виграш — у кількості запитів, які сервер тримає одночасно.
- **Не допомагає обчисленням.** Стиснення файлу, хешування пароля, обробка зображення завантажують процесор.
  Тут немає очікування, яке можна віддати, тож `async` лише додасть накладних витрат. Для важких обчислень
  потрібен окремий потік (`Task.Run`) або фонова черга.
- **Не створює потоків.** Найпоширеніша помилка — думати, що `await` запускає код «у фоні». Він лише каже:
  «коли ця операція завершиться, продовж звідси».

## Асинхронність «заразна»

Якщо метод викликає `await`, він сам стає асинхронним і повертає `Task`. Його викликач теж має використати `await` —
і так до самого верху: до дії контролера, обробника повідомлення чи `Main`. Спроба «зупинити поширення»
через `.Result` або `.Wait()` повертає блокування і в деяких середовищах призводить до дедлоку. Про це — у п'ятому уроці.

```csharp
public async Task<UserDto> GetProfileAsync(int id, CancellationToken ct)
{
    var user = await db.Users.FirstAsync(u => u.Id == id, ct);
    var avatar = await storage.GetUrlAsync(user.AvatarKey, ct);
    return new UserDto(user.Name, avatar);
}
```

## Типові помилки

| Помилка | Чому погано |
|---|---|
| `Task.Run(() => db.Users.First(...))` у контролері | Займає другий потік замість того, щоб звільнити перший |
| `async`-метод без жодного `await` | Компілятор попередить: метод виконується синхронно |
| Суфікс `Async` у синхронного методу | Вводить в оману тих, хто викликає |

## Практика

Відкрийте будь-який свій контролер і знайдіть виклики бази чи HTTP без `await`.
Замініть їх на асинхронні версії (`ToListAsync`, `FirstOrDefaultAsync`, `GetFromJsonAsync`) і пройдіть
ланцюжок викликів до верху, щоб жоден метод не блокував потік.
