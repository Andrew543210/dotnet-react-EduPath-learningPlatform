## Машина станів

Ключове слово `async` не існує на рівні IL — це інструкція компілятору переписати метод.
Компілятор перетворює кожен `async`-метод на структуру, що реалізує `IAsyncStateMachine`,
а тіло методу розрізає на шматки по кожному `await`.

```csharp
public async Task<int> CountAsync()
{
    var a = await LoadAsync();   // стан 0
    var b = await LoadAsync();   // стан 1
    return a + b;
}
```

Спрощено згенерований код виглядає так:

```csharp
struct CountAsyncStateMachine : IAsyncStateMachine
{
    public int state;
    public AsyncTaskMethodBuilder<int> builder;
    private int a;
    private TaskAwaiter<int> awaiter;

    public void MoveNext()
    {
        if (state == 0) goto Resume0;
        awaiter = LoadAsync().GetAwaiter();
        if (!awaiter.IsCompleted)
        {
            state = 0;
            builder.AwaitUnsafeOnCompleted(ref awaiter, ref this);
            return;                       // потік вільний
        }
    Resume0:
        a = awaiter.GetResult();
        // ... аналогічно для другого await
    }
}
```

Локальні змінні, які живуть між `await`, стають полями структури — так метод «пам'ятає», на чому зупинився.
Кожен `await` — це точка, у якій метод може «заснути» і пізніше продовжитися з того самого місця.

## Швидкий шлях: задача вже завершена

Зверніть увагу на перевірку `awaiter.IsCompleted`. Якщо задача, на яку чекає `await`, **уже завершена**,
метод продовжується синхронно, без жодного перемикання потоку і без виділення пам'яті під продовження.
Тому `await` на кешованому результаті (наприклад, значення з `IMemoryCache`, загорнуте в `ValueTask`) майже безкоштовний.

## Хто повертає Task

`AsyncTaskMethodBuilder` створює `Task`, який метод повертає викликачу одразу після першого «справжнього» очікування.
Коли машина станів доходить до `return`, білдер завершує задачу результатом. Якщо всередині вилетів виняток,
він не летить одразу — білдер зберігає його в задачі, і викликач отримає його в момент `await`.

```csharp
var task = FailAsync();   // виняток ще не викинуто
await task;               // викинуто тут
```

## Контекст синхронізації

Після `await` продовження виконується там, де вирішить `SynchronizationContext`:

- у **WPF і WinForms** контекст повертає продовження в UI-потік — тому після `await` можна змінювати елементи інтерфейсу;
- в **ASP.NET Core** контексту синхронізації немає, тож продовження виконується на будь-якому потоці пулу.

Саме захоплений UI-контекст разом із блокуючим `.Result` дає класичний дедлок — розберемо його в п'ятому уроці.

## Що з цього випливає на практиці

- `async` не робить обчислювальний код швидшим: машина станів лише звільняє потік під час очікування введення-виведення.
- Не позначайте метод `async`, якщо він просто повертає чужу задачу: `Task<User> GetAsync(int id) => repo.FindAsync(id);`
  обходиться без зайвої машини станів. Але всередині `using` або `try` потрібен саме `await`.
- Для гарячих шляхів, де результат часто вже готовий, використовуйте `ValueTask`.
