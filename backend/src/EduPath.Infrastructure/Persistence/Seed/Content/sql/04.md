## Читабельність важливіша за стислість

Аналітичні запити швидко обростають вкладеними підзапитами, які доводиться читати зсередини назовні.
Через тиждень автор сам не згадає, що рахує третій рівень вкладеності. CTE (Common Table Expression)
розв'язує це: конструкція `WITH` дає ім'я проміжному результату, і запит читається зверху вниз, як рецепт.

```sql
WITH first_orders AS (
  SELECT user_id, MIN(created_at) AS first_at
  FROM orders
  WHERE status = 'paid'
  GROUP BY user_id
)
SELECT date_trunc('month', first_at) AS cohort, COUNT(*) AS new_buyers
FROM first_orders
GROUP BY 1
ORDER BY 1;
```

## Кілька кроків

CTE можна ланцюжити: кожен наступний крок посилається на попередні.

```sql
WITH paid AS (
  SELECT * FROM orders WHERE status = 'paid'
),
user_stats AS (
  SELECT user_id, COUNT(*) AS orders, SUM(total) AS revenue
  FROM paid
  GROUP BY user_id
),
segments AS (
  SELECT user_id, revenue,
         CASE WHEN orders >= 5 THEN 'постійний'
              WHEN orders >= 2 THEN 'повторний'
              ELSE 'разовий' END AS segment
  FROM user_stats
)
SELECT segment, COUNT(*) AS users, SUM(revenue) AS revenue
FROM segments
GROUP BY segment;
```

Кожен блок можна перевірити окремо, замінивши фінальний `SELECT` на `SELECT * FROM user_stats LIMIT 20`.
Це найзручніший спосіб налагоджувати довгі запити.

## Підзапити: коли вони доречні

Короткий підзапит у `WHERE` часто читається природніше за CTE:

```sql
SELECT * FROM users
WHERE id IN (SELECT user_id FROM orders WHERE total > 10000);
```

**EXISTS** перевіряє наявність хоча б одного рядка й зупиняється на першому знайденому:

```sql
SELECT u.*
FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id
);
```

Пастка `NOT IN`: якщо підзапит поверне хоча б один `NULL`, `NOT IN` не поверне нічого. `NOT EXISTS`
поводиться передбачувано — віддавайте перевагу йому.

**Скалярний підзапит** повертає одне значення і може стояти в `SELECT`:

```sql
SELECT id, total,
       total - (SELECT AVG(total) FROM orders) AS diff_from_avg
FROM orders;
```

## Продуктивність

У PostgreSQL 12+ CTE за замовчуванням вбудовуються в основний запит, і оптимізатор обробляє їх так само,
як підзапити. Тож CTE — це про читабельність, а не про швидкість. Якщо проміжний результат використовується
кілька разів і рахується довго, `WITH ... AS MATERIALIZED` змусить базу обчислити його один раз.

Перевіряйте план виконання через `EXPLAIN ANALYZE`, а не покладайтеся на інтуїцію.

## Рекурсивні CTE

`WITH RECURSIVE` обходить ієрархії: категорії з підкатегоріями, оргструктуру, ланцюжки рефералів.

```sql
WITH RECURSIVE tree AS (
  SELECT id, parent_id, name, 1 AS depth FROM categories WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, c.parent_id, c.name, t.depth + 1
  FROM categories c JOIN tree t ON c.parent_id = t.id
)
SELECT * FROM tree ORDER BY depth, name;
```

## Практика

Розбийте покупців на сегменти «разовий / повторний / постійний» за кількістю оплачених замовлень
і для кожного сегмента порахуйте середній чек і частку виручки. Запишіть рішення через ланцюжок CTE
і перевірте кожен крок окремо.
