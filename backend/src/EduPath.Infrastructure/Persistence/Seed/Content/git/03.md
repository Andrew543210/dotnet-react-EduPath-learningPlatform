## Rebase переписує історію вашої гілки

Поки ви працювали над `feature/certificates`, у `main` з'явилися нові коміти. Можна влити `main`
у свою гілку через `merge`, а можна перебазувати гілку:

```bash
git switch feature/certificates
git fetch origin
git rebase origin/main
```

Git тимчасово знімає коміти вашої гілки, пересуває її на кінець `main` і застосовує коміти знову,
один за одним. Коміти гілки переносяться поверх свіжого `main`, і історія стає лінійною —
ніби ви почали роботу щойно.

```text
До:      A---B---C  main            Після:   A---B---C  main
              \                                       \
               D---E  feature                          D'---E'  feature
```

Зверніть увагу на `D'` і `E'`: це **нові** коміти з новими хешами. Зміни ті самі, але батько інший.

## Конфлікти під час rebase

Конфлікти розв'язуються так само, як під час злиття, але покроково — для кожного коміту окремо:

```bash
# виправити файли
git add src/CertificatePage.tsx
git rebase --continue    # перейти до наступного коміту
git rebase --abort       # повернути все як було
```

## Золоте правило

**Не робіть rebase гілки, яку вже забрали інші люди.** Rebase створює нові коміти. Якщо колега
вже побудував свою роботу на старих `D` і `E`, після вашого `push --force` у нього з'являться
дублікати комітів і заплутані конфлікти.

Свою особисту гілку, навіть уже опубліковану для pull request, ребейзити можна. Пушити її після rebase
треба з `--force-with-lease`: на відміну від `--force`, він відмовиться перезаписувати віддалену гілку,
якщо туди хтось встиг щось додати.

```bash
git push --force-with-lease
```

## Інтерактивний rebase: прибрати історію перед рев'ю

```bash
git rebase -i origin/main
```

Git відкриє список комітів гілки. Кожному можна призначити дію:

- `pick` — залишити як є;
- `reword` — змінити повідомлення;
- `squash` / `fixup` — об'єднати з попереднім комітом;
- `drop` — видалити.

Так коміти «wip» і «виправив опечатку» вливаються в осмислені зміни до того, як їх побачить рев'юер.

## Якщо щось пішло не так

Rebase здається страшним, бо «переписує історію». Насправді Git нічого не видаляє одразу:
`git reflog` зберігає кожне переміщення `HEAD` за останні 90 днів.

```bash
git reflog
# 7c1e2a9 HEAD@{0}: rebase (finish): returning to refs/heads/feature/certificates
# 51c0e3b HEAD@{5}: commit: Додати QR-код на сертифікат
git reset --hard HEAD@{5}
```

Знайдіть рядок перед початком rebase — і гілка повернеться точно в той стан.

## Практика

Створіть гілку з трьома комітами, один з яких — «виправлення опечатки». Через `git rebase -i`
об'єднайте його з попереднім комітом, потім перебазуйте гілку на оновлений `main`.
Після цього відновіть початковий стан через `git reflog`.
