## Один коміт — одна думка

Історія Git — це документація проєкту, яку читають частіше, ніж здається: під час рев'ю, пошуку
причини бага через `git bisect`, відкату невдалої зміни. Хороший коміт можна описати одним реченням.
Якщо в описі з'являється «і ще», коміт варто розділити.

Порівняйте дві історії однієї задачі:

```text
a1f3c09 fix
9b2e7d1 wip
4c81a22 зміни по формі + рефакторинг + поправив стилі
```

```text
e7d21b4 Додати валідацію email під час реєстрації
3a90f11 Винести перевірку пароля в окремий валідатор
c52b8e0 Показувати помилки полів під формою реєстрації
```

Другу можна прочитати як журнал рішень. Якщо валідація email зламала вхід для частини користувачів,
`git revert e7d21b4` прибере саме її, не зачепивши решти.

## Як готувати атомарні коміти

Робота рідко йде по одній задачі за раз: виправляючи форму, ви помічаєте опечатку в іншому файлі.
Не поспішайте з `git add .` — додавайте зміни частинами:

```bash
git status              # що змінено
git diff                # що саме змінено
git add -p              # переглянути зміни шматками й обрати потрібні
git diff --staged       # що потрапить у коміт
git commit
```

У режимі `git add -p` Git показує кожен фрагмент і питає: `y` — додати, `n` — пропустити,
`s` — розділити на менші шматки. Так з одного робочого каталогу виходять два-три охайні коміти.

## Повідомлення коміту

```text
Додати валідацію email під час реєстрації

Раніше сервер приймав адреси без домену, і листи підтвердження
поверталися з помилкою доставки. Тепер адреса перевіряється
на клієнті й на сервері тим самим правилом.
```

- **Заголовок** до 50–72 символів, у наказовому способі: «Додати», «Виправити», «Прибрати».
  Так історія читається як список дій, які застосовує коміт: «цей коміт — додати валідацію».
- **Порожній рядок** після заголовка — інструменти відрізняють заголовок від тіла саме так.
- **Тіло** пояснює *чому*, а не *що*: що змінено, видно з диффу.

Багато команд використовують Conventional Commits: `feat:`, `fix:`, `refactor:`, `docs:`, `test:`.
Префікс дозволяє автоматично збирати changelog і визначати номер версії.

## Чого не має бути в коміті

- Закоментованого коду «на потім» — історія Git і так його зберігає.
- Файлів IDE, збірки, логів — для них існує `.gitignore`.
- Секретів: паролів, ключів API, рядків підключення. Видалення в наступному коміті не допоможе —
  секрет залишиться в історії, тож його доведеться змінювати.

## Практика

Зробіть кілька різних змін у робочому проєкті, а потім розкладіть їх на окремі коміти через `git add -p`.
Перечитайте `git log --oneline` — чи зрозуміло з заголовків, що відбулося, без відкриття диффів?
