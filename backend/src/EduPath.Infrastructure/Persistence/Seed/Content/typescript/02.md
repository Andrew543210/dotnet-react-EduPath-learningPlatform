## Стан запиту без суперечностей

Типовий стан завантаження в React виглядає так:

```ts
type State<T> = {
  loading: boolean
  error?: string
  data?: T
}
```

Скільки комбінацій допускає цей тип? `loading: true` разом з `error` і `data` одночасно — що це означає?
Компоненту доводиться вгадувати, а тести — перевіряти неможливі стани.

**Дискриміноване об'єднання** описує лише допустимі стани:

```ts
type Request<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'error'; message: string }
  | { status: 'success'; data: T }
```

Тепер неможливо мати `data` і `message` одночасно. Поле `status` — **дискримінант**: літеральний тип,
за значенням якого TypeScript звужує об'єднання до одного варіанта.

```tsx
function CourseList({ request }: { request: Request<Course[]> }) {
  switch (request.status) {
    case 'idle':
    case 'loading':
      return <Spinner />
    case 'error':
      return <ErrorMessage text={request.message} />
    case 'success':
      return <Grid courses={request.data} />
  }
}
```

У гілці `'error'` доступне лише `message`, у `'success'` — лише `data`. Звернутися до `request.data`
в іншій гілці не дасть компілятор.

## Вичерпна перевірка з never

Через пів року хтось додасть стан `{ status: 'empty' }`. Як переконатися, що його обробили всюди?

```ts
function assertNever(value: never): never {
  throw new Error(`Необроблений варіант: ${JSON.stringify(value)}`)
}

switch (request.status) {
  case 'idle': /* ... */
  case 'loading': /* ... */
  case 'error': /* ... */
  case 'success': /* ... */
  default:
    return assertNever(request)
}
```

Якщо всі варіанти оброблено, у `default` змінна має тип `never`. Коли додають новий стан, у `default`
потрапляє `{ status: 'empty' }`, який не можна присвоїти `never`, — і перевірка `never` дає помилку
компіляції в кожному `switch`, де випадок не оброблено.

## Де ще знадобиться

- **Події й повідомлення**: `{ type: 'course.published'; courseId: number } | { type: 'payment.failed'; reason: string }`.
- **Результат операції** замість винятків: `{ ok: true; value: T } | { ok: false; error: E }`.
- **Кроки форми**: на кожному кроці свої обов'язкові поля.
- **Відповіді API**, де поле `kind` визначає форму решти даних.

## Типові помилки

- Дискримінант має бути **літералом** (`'error'`, `1`, `true`), а не `string`. Інакше звуження не працює.
- Не деструктуруйте об'єкт до перевірки: `const { status, data } = request` губить зв'язок між полями.
- Не додавайте опціональні поля «про запас» — кожне `?` повертає неможливі стани.

## Практика

Знайдіть компонент, який тримає `isLoading`, `error` і `data` окремими `useState`. Замініть їх одним станом
на дискримінованому об'єднанні з вичерпним `switch` і подивіться, скільки умов у розмітці стало непотрібними.
